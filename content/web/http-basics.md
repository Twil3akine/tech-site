HTTP は、ブラウザやプログラムがサーバーとデータをやり取りするための取り決めである。クライアントがリクエストを送り、サーバーがレスポンスを返す。Web ページの表示だけでなく、API の呼び出しでも同じ仕組みを使う。

## リクエストとレスポンス

HTTP の通信は大きく次の形になる。

```text
クライアント  -- リクエスト -->  サーバー
クライアント  <-- レスポンス --  サーバー
```

リクエストには、メソッド、URL、ヘッダー、必要に応じたボディが含まれる。レスポンスには、ステータスコード、ヘッダー、ボディが含まれる。

```console
$ curl -i https://example.com/
HTTP/2 200
content-type: text/html; charset=utf-8
...

<!doctype html>
<html>
...
</html>
```

実際の出力はサーバーによって異なる。`curl -i` はレスポンスのヘッダーも表示するため、状態を確認するときに使える。

## メソッド

メソッドはそのリクエストで何をしたいかを示す。

- `GET`: データを取得する。ボディは通常使わない
- `POST`: データを送信し、作成や処理の実行などを求める
- `PUT`: 対象のデータを指定した内容で置き換える
- `PATCH`: 対象のデータの一部を変更する
- `DELETE`: 対象のデータを削除する
- `HEAD`: `GET` と同じヘッダーだけを取得し、ボディは受け取らない
- `OPTIONS`: サーバーが対応している通信方法などを確認する

メソッドには、安全性と冪等性という性質がある。安全なメソッドはサーバーの状態を変更しない読み取り専用の操作である。冪等なメソッドは同じリクエストを繰り返しても、意図する結果が1回の実行と同じになる。

一般的には、`GET`、`HEAD`、`OPTIONS` は安全、`PUT` と `DELETE` は冪等とされる。`POST` は通常どちらでもない。`PATCH` は書き方によって冪等になる場合もあるが、常に冪等とは限らない。

API の定義はサーバー側の実装で決まるため、メソッド名だけで実際の動作を決めつけず、その API の仕様を確認する。

## ステータスコード

ステータスコードは3桁の数字で、最初の数字が結果の分類を示す。

- `1xx`: 情報。処理は継続している
- `2xx`: 成功
- `3xx`: リダイレクト。別の場所や追加の処理が必要
- `4xx`: クライアント側の誤り
- `5xx`: サーバー側の誤り

よく使うコードは次の通りである。

### 200 OK

リクエストは成功した。通常の取得や更新のレスポンスで使う。

### 201 Created

新しいリソースが作成された。`POST` で作成したときによく使う。

### 204 No Content

処理は成功したが、返すボディがない。削除や更新後のレスポンスで使うことがある。

### 301 Moved Permanently / 302 Found

別の URL へ移動する。`301` は恒久的な移動、`302` は一時的な移動を表す。用途に応じて `307` や `308` も使われる。

### 400 Bad Request

リクエストの形式や値が正しくない。JSON の文法エラーや必須項目の不足などが該当する。

### 401 Unauthorized

認証が必要、または認証に失敗した。名前は Unauthorized だが、主に「認証されていない」という意味である。

### 403 Forbidden

認証の有無にかかわらず、そのリソースへのアクセスが許可されていない。

### 404 Not Found

対象のリソースが存在しない。URL の誤りでも返る。

### 409 Conflict

現在の状態と競合するため処理できない。同じデータの重複作成や、更新同士の競合などで使う。

### 422 Unprocessable Content

リクエストの形式は読めるが、値の検証に失敗した。API によっては検証エラーにも `400` を使うため、仕様を確認する。

### 429 Too Many Requests

短時間のリクエストが多すぎる。一定時間待ってから再送する。

### 500 Internal Server Error

サーバー内部で予期しないエラーが起きた。具体的な原因はレスポンスだけでは分からないことが多い。

### 503 Service Unavailable

サーバーが一時的に利用できない。メンテナンスや過負荷の場合に返す。

## ヘッダー

ヘッダーは本体データに付ける補足情報である。名前と値をコロンでつなぐ。

代表的なリクエストヘッダーは次の通りである。

- `Accept`: 受け取りたい形式。例: `application/json`
- `Authorization`: 認証情報
- `Content-Type`: 送信するボディの形式
- `User-Agent`: クライアントの情報

代表的なレスポンスヘッダーは次の通りである。

- `Content-Type`: 返すボディの形式
- `Content-Length`: ボディのバイト数
- `Location`: リダイレクト先や作成したリソースの場所
- `Cache-Control`: キャッシュの扱い

ヘッダー名は大文字と小文字を区別しない。`Content-Type` と `content-type` は同じヘッダーを表す。

## ボディ

ボディは実際に送るデータ本体である。`POST`、`PUT`、`PATCH` では、JSON、フォーム形式、ファイルなどをボディに入れる。

JSON を送る例は次の通りである。

```console
$ curl -X POST https://example.com/items \
  -H "Content-Type: application/json" \
  -d '{"name":"book","price":1200}'
```

`Content-Type` は、受け取る側がボディの読み方を決めるために必要である。JSON 文字列を送っていても、`Content-Type` が合っていないと、サーバーが別の形式として処理することがある。

## URLとクエリ

URL には対象を表すパスと、条件を渡すクエリが含まれる。

```text
https://example.com/items?limit=20&sort=price
```

`items` がパス、`limit=20&sort=price` がクエリである。個別の対象を表す場合は、`/items/42` のようにパスへIDを含めることが多い。検索条件や表示件数のような補助的な条件は、クエリで渡すことが多い。

## 確認するときの順序

HTTP の通信で問題が起きた場合は、次の順で確認すると原因を分けやすい。

1. メソッドと URL が仕様と合っているか
2. ステータスコードが成功、クライアント側、サーバー側のどれか
3. `Content-Type` とボディの形式が合っているか
4. 認証や権限が必要な API か
5. レスポンスのボディにエラー内容が書かれていないか

ステータスコードだけではなく、ヘッダーとボディをあわせて読むことで、形式の誤り、認証の問題、サーバーの障害を区別できる。
