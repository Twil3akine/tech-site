E0308 は、期待される型と実際の値の型が一致しないときに発生するコンパイルエラーである。エラーコードの説明は[公式ドキュメント](https://doc.rust-lang.org/error_codes/E0308.html)で確認できる。最初に、関数の戻り値でこのエラーになる例を示す。

これはコンパイルエラーになる。

```rust
fn describe(count: i32) -> String {
    if count > 0 {
        String::from("あります")
    } else {
        0
    }
}

fn main() {
    assert_eq!(describe(3), "あります");
}
```

## エラー文を読む

コンパイラは概ね次のような診断を出す。実際の行番号や補足表示は Rust のバージョンや出力設定で異なるが、それぞれの行が示す役割は同じである。

```text
error[E0308]: mismatched types
 --> src/main.rs:5:9
  |
1 | fn describe(count: i32) -> String {
  |                            ------ expected `String` because of return type
  |
5 |         0
  |         ^ expected `String`, found integer
```

読み方は、期待される型（expected）と実際の型（found）の対比である。この例では戻り値の型が `String` と宣言されているため、`if` の各分岐も `String` を返さなければならないが、`else` 側が整数を返している。診断には変換メソッドを使う提案（help）が付くこともある。

## なぜ起きるか

Rust は型の異なる値を暗黙には変換しない。整数を浮動小数点数として使ったり、文字列リテラルを `String` として渡したりすると、その場で E0308 になる。expected 側の型は、変数の型注釈、関数の引数や戻り値の宣言、`if` 式のもう一方の分岐など、周囲の文脈から決まる。

場面ごとに直し方が違うため、以下では代表的な4つの場面に分けて示す。

## 直し方1: 戻り値と分岐の型をそろえる

最初の例は、`else` 側も `String` を返すよう直す。

```rust
fn describe(count: i32) -> String {
    if count > 0 {
        String::from("あります")
    } else {
        String::from("ありません")
    }
}

fn main() {
    assert_eq!(describe(3), "あります");
    assert_eq!(describe(0), "ありません");
}
```

`if` 式は両方の分岐が同じ型を返さなければならない。数値を文字列として返したい場合は、`0` と書く代わりに `count.to_string()` のように変換を明示する。

## 直し方2: 数値型を変換する

`i32` の値を `f64` の変数に入れるような、数値型同士の代入でも暗黙変換は行われない。

これはコンパイルエラーになる。

```rust
fn main() {
    let count: i32 = 4;
    let rate: f64 = count;
    println!("{rate}");
}
```

診断は「expected `f64`, found `i32`」となり、変換方法の提案も付く。直し方は `as` によるキャストか、`From` を使う変換である。

```rust
fn main() {
    let count: i32 = 4;

    // as でキャストする
    let rate: f64 = count as f64;
    assert_eq!(rate, 4.0);

    // f64::from でも変換できる
    let rate2 = f64::from(count);
    assert_eq!(rate2, 4.0);
}
```

`as` は切り捨てや桁落ちが起きる変換でも警告なく通るため、値の範囲が問題になる場合は `TryFrom` を使う変換や、変換後の検証を組み合わせる。

## 直し方3: 参照と値をそろえる

文字列リテラルは `&str` であり、`String` ではない。`String` が必要な場所にリテラルをそのまま入れると E0308 になる。

これはコンパイルエラーになる。

```rust
fn main() {
    let text: String = "hello";
    println!("{text}");
}
```

直し方は、所有する文字列を作る変換を入れることである。

```rust
fn main() {
    // to_string で String に変換する
    let text: String = "hello".to_string();
    assert_eq!(text, "hello");

    // String::from でも同じ変換ができる
    let text2: String = String::from("hello");
    assert_eq!(text2, "hello");
}
```

逆に、関数の引数が `String` を要求しているのに `&str` や `&String` を渡して E0308 になることもある。その場合は渡す側を変換するか、関数の引数を `&str` に変えて借用で受け取るか、どちらが適切かを考える。読むだけの関数なら、引数を `&str` に変える方が呼び出し側の負担が少ない。

## 直し方4: OptionとResultの中身と取り違えない

`Option<T>` や `Result<T, E>` は中身の型とは別の型である。中身の型としてそのまま受け取ると E0308 になる。

これはコンパイルエラーになる。

```rust
fn main() {
    let value: i32 = Some(42);
    println!("{value}");
}
```

診断は「expected `i32`, found `Option<{integer}>`」となり、包まれていることが分かる。直し方は、中身を取り出す処理を挟むことである。

```rust
fn main() {
    // 値がなければデフォルト値を使う
    let value: i32 = Some(42).unwrap_or(0);
    assert_eq!(value, 42);

    let missing: Option<i32> = None;
    assert_eq!(missing.unwrap_or(0), 0);
}
```

`HashMap` の `get` が `Option<&V>` を返すのも同じ構造で、取得した値をそのまま数値として使おうとすると E0308 になる。`Result` と `Option` を互いに代入しようとした場合も E0308 になり、その場合は `ok` や `ok_or` で変換してから代入する。

E0308 が出たら、診断の expected と found を読み、どちらの型にそろえるべきかを先に決める。そろえる方向が決まれば、変換を入れるのか、宣言側の型を変えるのか、包まれた値を取り出すのかが自然に決まる。
